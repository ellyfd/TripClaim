# TripClaim 分階段發布與回復手冊

## 發布閘門

- 程式：lint、build、全部測試與 CSS audit 通過。
- 資料：migration 為 additive；未知主檔值進例外佇列，不靜默轉換。
- 裝置：完成 `DEVICE_QA.md` 的自動檢核；內部測試帳號完成手機 smoke test。
- 安全：附件只經登入授權串流，回應使用 `private, no-store` 與 `nosniff`。
- 人員：新帳號必須同時存在於 Sites 網站存取名單與 TripClaim 系統人員主檔；兩邊使用相同 Email。

## 漸進啟用

1. 內部 3–5 人：各完成一趟「行前 → 旅途中 → 回國後」演練。
2. 觀察 48 小時：上傳失敗率、OCR 待確認率、孤兒附件、匯出差額皆為可接受範圍。
3. 擴至一個部門；保留舊流程作為短期備援。
4. 指標穩定後全面啟用；舊流程僅唯讀查詢。

## 停止條件

- 任一使用者可讀到他人的個人附件或卡片資料。
- 報支總額與明細不一致。
- 原始幣別或原始文件遺失。
- 上傳成功卻沒有文件或費用紀錄。
- PWA 重啟後離線佇列遺失。

出現任一條件即停止擴大，保留資料並執行回復。

## 回復演練

1. 記錄目前 Sites `version_id`、GitHub main SHA 與資料 migration 版本。
2. 從 Sites 部署紀錄選擇前一個已成功且通過驗收的版本重新部署。
3. 不回滾資料庫 schema；新欄位保持向後相容，舊版忽略即可。
4. 驗證登入、我的出差、文件下載、既有費用與匯出。
5. 對失敗版本建立修復分支；修復通過完整閘門後再漸進發布。

正式回復會切換生產版本，只有在事故或獲得產品負責人明確授權時執行；日常發布只做流程演練與前一成功版本可用性確認。
