# TripClaim 裝置驗收矩陣

本矩陣把桌機的「全貌與批次整理」和手機的「今日、拍照、例外確認」分開驗收。每次發布前先執行 `npm test`；正式站需由有權限的測試帳號完成下列人工 smoke test。

| 裝置／模式 | 尺寸 | 必驗流程 | 通過條件 |
| --- | --- | --- | --- |
| iPhone Safari | 390×844 | 我的出差 → 今日 → 拍照／上傳 → 待辦 | 兩次點擊內進入上傳；Bottom Navigation 固定；Bottom Sheet 不被安全區遮住 |
| Android Chrome | 412×915 | 今日切日 → 新增活動 → 離線上傳 → 恢復連線 | 單日時間軸；44px 點擊區；顯示「已保存，辨識中」並續傳 |
| PWA standalone | 390×844 / 412×915 | 加到主畫面後冷啟動、離線啟動、背景回前景 | 無瀏覽器工具列依賴；離線頁可達；待上傳資料不遺失 |
| 小型桌機 | 1024×768 | 行程全貌、工具抽屜、報帳流水帳 | 無整頁水平捲動；右欄收合而非擠壓主表 |
| 一般桌機 | 1280×800 / 1440×900 | 行程、核對、批次整理、ZIP 匯出 | 主工作區置中；字級一致；功能集中右側 |
| 大型桌機 | 1920×1080 | 31 天行程與 1,000 筆費用 | 主欄與 320px 工具欄穩定；長列表捲動流暢 |

## 發布前快速檢核

1. `npm run lint && npm test`
2. 使用有權限測試帳號在 Safari、Chrome 各上傳一張測試收據。
3. 關閉網路上傳第二張，確認顯示已保存；恢復網路後確認自動同步。
4. 同一筆費用切換原始／申報幣別，確認原幣不消失。
5. 刪除一般非 travel 測試費用，確認其單據一併移至可復原狀態且有二次確認。
6. 上傳一張含去程／回程或轉機的機票，確認每個實際 departure → arrival 航段都直接出現在共同行程，整張票只形成一筆本人報支。
7. 從任一去程／回程航段執行刪除，確認同一 source order 的所有航段、共同行程、travel expense、正式文件與附件全部消失，且 travel trash 無法復原。
8. 重新上傳與第 6 步相同的機票，確認得到新的 document，畫面不載入舊 order；按「確認並同步」後，共同行程只能存在這次新 order 的航段。
9. 上傳住宿文件，確認行程 startsAt = 入住日 15:00、endsAt = 退房日 11:00；城市／地址缺失時仍可同步。
10. 若測試環境可模擬 R2 delete failure，確認 formal graph 仍立即從 UI 消失、cleanup 顯示 pending，且 failed object key 有 pending deletion tombstone；後續 travel 操作會再次重試清理。
11. 桌機 1024、1280、1440、1920px 逐一確認無整頁水平捲動。

## Travel Order 真人 smoke test 最小資料集

- 1 張來回機票（至少 2 航段；若有轉機更佳）。
- 1 張住宿訂單（清楚包含 check-in / check-out 日期）。
- 同一張機票檔案保留一份，供「刪除後重新上傳同檔」測試。

驗收順序固定為：**上傳 → 確認同步 → 檢查行程 → 刪除任一航段 → 確認整單消失 → 重傳同檔 → 再次確認同步 → 確認只有新資料**。

雲端自動瀏覽器若被 Sites 登入頁阻擋，不得繞過登入；該輪以自動裝置契約測試為基線，真人 smoke test 留在發布觀察紀錄中。
